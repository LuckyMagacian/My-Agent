## 4. 问题清单

### 问题 1【重要】头部留痕指针行规约自相矛盾、措辞偏离七份先例固定措辞且未定义所称「固定格式」

- **位置**：组件 §3.4 三条（交付物 L94~96）；头部「版本演进留痕」行（L22）；对照 §1 表末行（L35）
- **证据摘录**：
  - §3.4 条一：「文档头部**仅保留**当前版本号与对齐基准」；§3.4 条三：「头部留痕指针行统一表述为指向本文（references/version-evolution.md）的固定格式」——同节内条一的「仅保留」口径在字面上排除条三强制的留痕指针行，条款间自相矛盾；
  - 与组件自身 §1 表「头部仅保留当前版本与对齐基准 **+ 一行留痕指针**（指向本文）」直接冲突；
  - 与工作区实况冲突：七份既有头部均含留痕指针行，SKILL.md / requirements-stage / design-stage / development-stage / testing-stage 另含文档属性、交付状态行；changelog/2026-08-07.md L5 的既有成句「文档头部此后仅保留当前版本号与对齐基准」本身即为不精确先例，组件照搬后与自身条三冲突被放大；
  - 条三所称「固定格式」未给出模板文本，规约不可直接执行；
  - 头部留痕行「本文即版本演进留痕的权威文档，**各组件头部留痕指针指向本文**」：① 偏离七份先例唯一固定措辞范式「本文版本演进注释已迁移至 skill 的 changelog/ 目录（按改动日期命名，一次改动的全部条目记入当日文件），头部仅保留当前版本与对齐基准」（指向式 + 括号用法注，无一例外）；② 断言句描述的「各组件指针指向本文」状态在落盘前尚不成立（现七份头部均指向 changelog/），若指针改造未与落盘同批完成即构成失实表述；③ 本文自身头部不含指向 references/version-evolution.md 的指向式指针，不满足验收标准⑤「留痕指针行」要素与条三对「各组件」的要求（本文亦属组件）。
- **期望标准**：验收标准①「规约段与既有惯例无矛盾」、⑤「头部留痕指针行符合既有惯例」；组件条款不得自相矛盾；规约给出的格式须可执行（含模板或明确比照样例）；组件不得对自身未落地状态作失实断言。
- **修改方向**：
  1. §3.4 条一改「文档头部仅保留当前版本号、对齐基准与一行留痕指针（演进注释不写入头部）」，并与 §1 表措辞统一；
  2. 条三给出固定格式模板，比照先例句式，例如：「版本演进留痕：本文版本演进事务由 references/version-evolution.md 承载（版本规约、changelog 用法与总账；明细见 skill 的 changelog/ 目录，按改动日期命名），头部仅保留当前版本与对齐基准」；
  3. 本组件头部留痕行改用上述指向式固定格式（指向自身路径），删除「各组件头部留痕指针指向本文」的断言句（该事实由落地时的指针改造承载，改在 §3.4 / 变更说明中以义务口径表述）。

### 问题 2【重要】§2.2 纯元数据同步口径未覆盖「新增登记行」，与 changelog 当日新增第 12 条先例冲突，建立事件自身版本处置不可判定

- **位置**：组件 §2.2 升版触发表第 2 行（交付物 L55），联动 §2.4 第 2、3 项（L67~68）
- **证据摘录**：
  - §2.2：「纯元数据同步（对齐基准行、登记表**版本列**、留痕指针、§12 关系行）→ 不升该文档机制版本」——枚举以「版本列」为限，未含「新增行」；
  - §2.4 第 2 项同样仅「SKILL.md §2 组件登记表**版本列**」、第 3 项仅「§12 登记表对应行（…反向同步行——…版本号）」，均不覆盖新增行；
  - 工作区先例：changelog/2026-08-07.md 第 12 条将「context-system v2.3.3 §12 **增**执行检查清单行并同步 SKILL.md v1.0.5」整体标注「仅元数据」，未升 context-system 版本；而 SKILL.md v1.0.5（第 11 条）承载「§2 冲突规则段增辅助工具文件声明」升号，先例中不存在「纯新增登记行」单独定性的升版记录；
  - 后果：本组件建立落地时须在 SKILL.md §2 登记表与 §12 各**新增一行**，该动作按 §2.2 字面不属纯元数据（不在枚举），亦不属「机制增量（行为定义新增/修改/删除）」（登记行不定义行为），两分法出现分类缺口，落地时 SKILL.md 升号范围（仅例外性升号 vs 机制增量升版）与 context-system 是否升版不可判定。
- **期望标准**：升版触发两分法须对建立事件涉及的全部动作闭合可判定，且不得与既有 changelog 条目定性冲突（验收标准①）。
- **修改方向**：§2.2 纯元数据枚举扩为「对齐基准行、登记表版本列**与新增登记行**、留痕指针、§12 关系行（含新增行）」，并注明依据先例：changelog/2026-08-07.md 当日新增第 12 条（§12 新增行定性为仅元数据）；SKILL.md 因例外条款（每次改动升号）自然承载登记行新增，无需另设口径。

### 问题 3【重要】引用侧同步点位计数文内矛盾：§4.9「七处」 vs §2.4 五项与摘要「五类」

- **位置**：组件 §4.9 总账自记行摘要（交付物 L206）；对照 §2.4（L64~70）与交付物第 4 段摘要（L244）
- **证据摘录**：
  - §4.9 v1.0 行摘要：「……总账；引用侧**七处**同步」；
  - §2.4 同步义务为五项编号列表（对齐基准行 / 登记表版本列 / §12 对应行含反向 / cross-reference-index 末次校验与条件性分组行 / changelog 当日条目）；
  - 交付物 §4 摘要：「引用侧**五类**同步点位」；
  - 「七处」无法由 §2.4 五项经任何稳定口径导出（若将第 4 项两动作拆分并另计他项亦无规约依据），同一交付物内两处计数互斥。
- **期望标准**：组件内对同一事实的计数须一致且可由规约条款导出（无失真，验收标准①②）。
- **修改方向**：统一以 §2.4 五项为准，§4.9 摘要删「七处」改为「引用侧五类同步点位（§2.4）」或径改「引用侧同步（§2.4）」；交付物 §4 摘要同口径。

### 问题 4【重要】简洁性审视：规划仲裁编号注记可删除而行为定义无损

- **位置**：§2.2 第 2 行括注「（P2-1 裁定固化：机制正文零改动即不升版）」与 §2.3 括注「（P2-4 裁定固化）」（交付物 L55、L60）
- **证据摘录**：两处「P2-N」为本实例规划阶段仲裁产物（arbitration-plan-r2）的内部编号，组件读者无从在 skill 文档体系内解析其指涉；规则本体（「机制正文零改动即不升版」「行粒度以源明细形态为准、无失真优先」）在句中已完整表述，删除编号注记后行为定义零损失；原子组件须自包含（约束⑤同向要求：不依赖实例内部材料）。
- **期望标准**：简洁性审视义务（《工作模式》§10.3）——可删除而行为定义无损的条款逐条列出；定稿组件不得携带实例内部谱系注记。
- **修改方向**：删去两处「P2-1 裁定固化」「P2-4 裁定固化」字样，保留规则本体；裁定溯源如需留痕，由 changelog 本批次条目与实例归档承载（不随组件文档携带，§5.2 条二既有口径）。

### 建议 1【建议】留痕指针不承载版本号，本文升版时 §2.4 同步点位无版本承载位

- **位置**：§3.4 条三 + §2.4（交付物 L96、L64~70）
- **证据摘录**：指针设计为「一行留痕指针（指向本文）」，无版本字段；各引用方头部对齐基准行均不登记 version-evolution 版本，则本文日后升版时，§2.4 第 1 项「引用方文档头部对齐基准行」无适用对象，引用侧不存在承载本文新版本号的点位。
- **修改方向**：二选一——① 固定格式中携现行版本（如「references/version-evolution.md 现行 vN」），升版时按 §2.4 同批更新；② 在 §2.4 / §3.4 显式声明「本文升版不要求引用侧版本承载，留痕以总账 + changelog 为准」，使该缺口成为明示设计而非遗留。
