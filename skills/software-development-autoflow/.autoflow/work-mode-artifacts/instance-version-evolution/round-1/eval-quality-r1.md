## 4. 问题清单（共 10 条：阻断 0 / 重要 7 / 建议 3）

### Q1【重要】§2.1 版本号语义与被治理对象的实际版本形态矛盾
- 位置：组件 §2.1（交付物文件 L41–48）
- 证据摘录：§2.1 定「v0.x：评估期草稿版本」「v1.0：首次收敛定稿交付版本」。但 `references/requirements-stage.md` 头部载明「经 work-mode 四轮双视角评估定稿……并经人工确认定稿」（现行 v0.8.7）；
`references/design-stage.md` 头部载明「v0.7 减法轮后 R7 9.5/8.5 收敛……并经人工确认定稿」（现行 v0.9），changelog【迁移】design-stage v0.7.3 行记录其已收敛定稿并交付至 skill 根目录。两文档均为收敛定稿后交付、并以直接补丁持续升版（v0.8.7/v0.9），按 §2.1 口径却归入「评估期草稿」。
- 期望标准：规约条款与被治理对象的实际状态逻辑自洽（验收标准①规约段完整、版本号规则正确）。
- 修改方向：§2.1 补例外口径——「于 v0.x 收敛定稿的组件（requirements-stage、design-stage 先例）沿用 v0.x 续号，后续升版按 §2.2」；或将 v0.x 改述为「评估迭代期版本（含评估期定稿组件的 v0.x 续号）」。

### Q2【重要】引用侧同步点位枚举不完整且与 §1 引用不一致
- 位置：组件 §1 关系表第 3 行（L32）、§2.4（L62–70）
- 证据摘录：§1 宣称《上下文体系》「§4 / §12……两处均为引用侧同步点位（§2.4）」，但 §2.4 五类枚举仅列 §12 登记表、未列 §4 存储布局树；§2.4 第 4 类仅覆盖交叉索引「末次校验行版本集（无条件）」与「被引方分组行新增（仅当新组件被其他组件以《别名》§章节形式引用时）」，
未覆盖「既有组件新增被引用章节需同步引用行」之情形——实际先例：changelog 当日新增条目 9「交叉引用索引表末次校验更新并增 SKILL.md → 《需求阶段》§5.0 引用行、《设计阶段》§5.1 引用计数同步」。佐证：《上下文体系》§4 布局树（L85–99）对已存在的 cross-reference-index.md、execution-checklist.md 两文件即无行，建立类同步点位确无规约承载。
- 期望标准：验收标准④（引用侧同步设计完整）；文内引用自洽。
- 修改方向：§2.4 区分升版类与建立类两枚举——建立类补列《上下文体系》§4 布局树行、§12 登记表行、SKILL.md §2 登记表行；升版类第 4 项补「被引组件新增被引章节时交叉索引对应引用行/计数同步」；并使 §1 引用表述与 §2.4 一致。

### Q3【重要】§4.9 明细指针写死 2026-08-07，与 §3.1 命名规则矛盾
- 位置：组件 §4.9 表行（L206）
- 证据摘录：明细列作「changelog/2026-08-07.md【当日新增】（本批次条目，定稿时写入）」；而 §3.1 定文件「按改动日期命名」「一次改动的全部条目记入当日文件」。本组件定稿日期晚于 2026-08-07（本实例评估与定稿发生于其后），定稿批次当属定稿当日文件。
- 期望标准：总账明细指针与自定义的 changelog 用法规约一致。
- 修改方向：明细列改为「changelog/<定稿当日>.md【当日新增】（本批次条目，定稿时写入）」，日期留占位、定稿时填入。

### Q4【重要 · 简洁性】规划裁定溯源标注可无损删除
- 位置：§2.2「（P2-1 裁定固化：……）」、§2.3「（P2-4 裁定固化）」（L55、L60）
- 可删论证：两处裁定编号为规划过程溯源；规则条款本身（「不升该文档机制版本」「行粒度以源明细形态为准」）已承载完整行为定义，删除不损任何行为；过程细节依 §5.2 项 2 分工原则由归档与 changelog 承载。
- 期望标准：简洁性审视义务——可删除而行为定义无损的条款应删除。
- 修改方向：删两处裁定编号标注（「机制正文零改动即不升版」口径说明可保留）。

### Q5【重要 · 简洁性】先例佐证注记可无损删除

### Q6【重要 · 简洁性】实例专属归档指针可无损删除

### Q7【重要 · 简洁性】总账行内形态元注记可无损删除
- 位置：§4.3 v1.0–v1.3 行「（源明细合并行，……）」、§4.5 v0.2–v0.6 行「（源明细合并行）」、§4.5（元数据）行「（源明细单行）」（L131、L160、L165）

- 修改方向：删三处「（源明细……）」元注记，保留内容摘要本体。

### Q8【建议】§4.5 拆分源明细单行，偏离「以源明细形态为准」口径
- 位置：§4.5 首两行（L159–160）
- 证据摘录：changelog【迁移】design-stage.md 首条为单行「v0.1 首版；v0.2–v0.6 五轮双视角评估修订（……）」；总账拆为「v0.1」「v0.2–v0.6」两行。信息无失真，但与裁定 B 及 §2.3「以源明细形态为准」严格不符；§2.3 以「design-stage v0.2–v0.6」为源明细合并行之例，亦与源形态（该行实含 v0.1）不完全吻合。
- 修改方向：二选一——① 按源形态将 v0.1 与 v0.2–v0.6 同行入总账；② 在 §2.3 明示「行内版本区间合并段不拆分，区间外相邻版本可独立成行」，使执行口径统一。

### Q9【建议】§4.9 摘要「引用侧七处同步」数字无文内锚点
- 位置：§4.9 v1.0 行摘要列（L206）
- 证据摘录：「……总账；引用侧七处同步」。文内仅 §2.4 五类（升版类）枚举，无与「七处」对应的展开枚举，读者不可核验。
- 修改方向：与 Q2 修复合并，展开建立类同步点位枚举；或改定性表述（「引用侧同步见 §2.4」）。

### Q10【建议】changelog/ 目录建立事件入册口径未明示
- 位置：§4 覆盖集合声明（L102）、§4.8（L195–200）
- 证据摘录：覆盖集合钉死「七份版本文档 + 本文自身 + 两个工具文件建立事件」；但 changelog 当日新增条目 3「新建 changelog/ 目录与本文件」同为无版本号建立事件，与两个工具文件建立事件同类而未入册，口径不对称。
- 修改方向：二选一——① §4.8 增「changelog/ 目录建立」行；② 覆盖集合声明中明示「changelog/ 为明细库本体，其建立事件由本库条目 3 自承载、不入总账」。
