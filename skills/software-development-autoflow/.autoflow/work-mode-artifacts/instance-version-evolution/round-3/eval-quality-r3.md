## 一、逐问题清单

### P1（阻断）版本总账（§4）与 changelog/ 现存文件事实系统性背离，指针、版本号、概述、行粒度四维失真
- 位置：组件 §4.1~§4.7 全部历史行（§4.8、§4.9 除外）
- 描述：
  1. **指针断链**：§4.1~§4.7 历史行明细指针指向 changelog/2026-08-04.md、2026-08-05.md、2026-08-06.md，三文件均不存在；changelog/ 现存唯一文件为 2026-08-07.md，且该文件【迁移】节明确承载七份文档迁入的全部演进明细。总账作为「明细指针」索引对既有历史版本整体不可解析。
  2. **版本号无据**：大量总账版本号在 changelog 任何条目中不存在。抽样（均为与【迁移】节/【当日新增】节逐行比对所得）：§4.1 之 v0.1~v0.5、v0.5.1、v0.6、v0.6.1（现存记录仅 v0.1、v0.2、v1.0、v1.0.1、v1.0.2，迁出前版本 v1.0.2）；§4.3 之 v1.3.1、v2.0.1、v2.0.2~v2.0.3（现存链路为 v2.0→v2.1→v2.2→v2.3→v2.3.1→v2.3.2）；§4.4 之 v0.5.1~v0.5.3；§4.5 之 v0.3、v0.3.1、v0.4、v0.4.1~v0.5（现存记录为「v0.1 首版；v0.2–v0.6 五轮双视角评估修订」单行合并形态 + v0.7 起逐版）；§4.6 之 v1.0.1~v1.0.3；§4.7 之 v0.5、v0.6（测试阶段现存记录为 v0.1~v0.4 + v1.0）。
  3. **概述与明细直接矛盾**：§4.1 v1.0.1 概述为「外部二次评估修订」，而现存明细 v1.0.1 为「组件文件迁移至 references/ 目录（仅元数据同步）」；§4.1 v1.0 概述「九章节结构」与现行 SKILL.md 十一章结构不符；§4.4 v0.8.6 概述为「既有需求文档输入询问补全」，而现存明细 v0.8.6 为「指令结构重排（机制零改动）」，外部输入问询实属 v0.8.7；§4.4 v0.4.1 概述为「迁移至正式结构」，现存明细 v0.4.1 为「补角色分离说明」；§4.5 v0.1~v0.2 概述含「过度设计减法整改」，现存明细该整改属 v0.7；§4.2、§4.3、§4.6、§4.7 各行概述亦与对应明细主题普遍错位（如 §4.7 v1.0 概述「外部输入询问与断点恢复加固」无明细依据）。
  4. **行粒度双向违反组件自身 §2.3**：源明细为合并形态者被拆分（§4.5 将「v0.2–v0.6」单行拆为 v0.1~v0.2 / v0.3 / v0.3.1 / v0.4 多行）；源明细为分立形态者被合并（§4.6 源 v0.1~v0.9 逐版分行被并为「v0.1~v0.6」一行；§4.7 源 v0.1~v0.4 分行被并为「v0.1~v0.6」一行；§4.3 源 v2.1~v2.3.2 分行被并入「v2.0.2~v2.3.2」一行）。
- 分级理由：总账是任务指令第①③项的落点，其「指针」职能整体失效、「记录」职能与唯一权威明细（组件 §5.2 自认 changelog 明细为机制细节唯一权威）大面积冲突，属机制正确性问题。§4.8（两件工具建立事件，指针与事实相符）与 §4.9 不受影响。
- 整改方向（不含改写文本）：以 changelog/2026-08-07.md【迁移】节与【当日新增】节的现存条目为唯一事实源，按组件自身 §2.3 粒度规则整体重建 §4.1~§4.7 的版本行、概述与指针，不得引入现存明细之外的版本号。

### P2（建议）§2.4 第 4 项同步点位表述与《上下文体系》§12 实际形态不符
- 位置：组件 §2.4 第 4 项
- 描述：现行 context-system.md §12 为「文档 | 关系」表，版本号内嵌于各行文档名单元格（如「work-mode.md v1.6.2」），不存在独立的「版本行」；SKILL.md 升号时的反向同步落点也是其既有关系行的版本内嵌值，而非独立「反向同步行」。点位本身真实存在且同步义务成立，但「版本行」「反向同步行」的形态表述与现状不符，执行者按字面查找将无所指。
- 整改方向：将该点位的形态表述对齐为「§12 关系表中对应文档行的版本号」口径。

### P3（建议）§2.1「沿用《上下文体系》§4 既有惯例」引用源失准
- 位置：组件 §2.1 表 Y/Z 增量行括注
- 描述：现行 context-system.md §4 为「存储布局与隔离域」，含 changelog/ 布局行与命名注释，但不承载 Y/Z 升段位版本号惯例；该括注将惯例渊源指向了一个不承载此惯例的章节。
- 整改方向：删除该括注或将惯例渊源改指为既有实践/本文自身。

### P4（建议）§3.2 逐条目变更性质标签与 changelog/ 既有实践形态不一致
- 位置：组件 §3.2
- 描述：现行 changelog/2026-08-07.md 的变更性质以批次分节标题承载（【迁移】/【当日新增】），条目自身不携带性质标签，且全文未出现【修订】标签；§3.2 要求「每条含……变更性质（【新增】/【修订】/【迁移】）」，与既有实践形态不一致，且【新增】与既有分节标签【当日新增】字面不同。规约其余要素（文件+版本号、迁移类原→新版本、摘要、机制要点、§指针、批次分节）均与既有实践相符。
- 整改方向：性质标签口径与既有文件形态对齐（批次承载或逐条承载二选一并统一字面），避免规约落盘后与现存文件互证失败。

### P5（建议）§3.4「头部承载三项」与固定模板尾句「头部仅保留当前版本与对齐基准」存在字面张力
- 位置：组件 §3.4
- 描述：§3.4 规则声明头部承载现行版本、对齐基准、留痕指针行共三项，而紧随的固定模板尾句称「头部仅保留当前版本与对齐基准」，未计入指针行自身。该尾句与既有各组件头部现行措辞一致（属既有实践沿用），且经减法轮 D-2 合并后全文仅模板一处承载，但组件自我描述两处口径字面不自洽，按字面执行会产生「指针行是否属头部承载项」的歧义。
- 整改方向：统一两处的项数口径（模板尾句计入或不计入指针行均可，取其一即可）。

### P6（建议）§1 分工表建立事件注释不对称

- 描述：§1 表为执行检查清单注明「其建立事件已记入 §4 总账」，而对交叉引用索引（§4.8 同样记录其建立事件）无同口径注释，减法后残留表述不对称。
- 整改方向：两工具行口径取齐（同注或同删）。
