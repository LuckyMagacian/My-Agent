## 4. 逐条问题

### 建议级 4.1 —— TI 测试代码实现者/来源未定义，C1 闭环存在归属缺口

- **位置**：`references/testing-stage.md` §4.5「执行归属」段（L95）；关联 `references/design-stage.md` §4.8（L138）、`references/testing-stage.md` §3（L47）
- **原文摘录**：
  - testing-stage L95：「TI-NNN 用例（接口集成测试）由 **Main Agent（编排者）** 在 §5.1.5 测试基础就绪核验通过后、§5.4 条目实例启动**之前**，以阶段层任务一次性执行（不分配至条目实例——TI 可能跨 REQ-NNN）；执行命令与预期结果取自设计阶段 `test-cases.md` §4.8 第 2 项（接口集成测试用例）的「核验方式」字段」
  - design-stage §4.8 L138：「**职责边界**：本节仅承担"用例设计"职责（用例标识、核验方式、依赖声明），**不涉及测试代码实现**——测试代码编写归测试阶段。」
  - testing-stage §3 L47：「测试实例的执行者直接在工作空间工程内编写测试代码」
- **期望标准**：I-5 修复定义了 TI「谁执行、何时执行」，但未定义「TI 的测试代码由谁编写、何时编写」。设计阶段明确不写代码；条目实例（测试代码编写者）在 TI 执行之后才启动；§4.4 测试代码清单虽要求引用 TI-NNN ID，但未指明 TI 代码的编写主体。若 TI 核验命令依赖的测试代码尚不存在，Main Agent 在执行时无代码可运行，且 §4.5 第 3 段故障类别仅四类（数据库/token/域名/mock），非依赖类执行失败的处置路径亦未定义——形成阶段间闭环缺口。
- **修改方向**：在 §4.5「执行归属」段补一句明确 TI 测试代码归属，例如：「TI-NNN 用例的测试代码由 Main Agent 在 §5.2 测试基础设施前置建立后、执行前按设计用例「核验方式」字段编写（优先沿用/扩展工程既有测试设施），代码位置符合 §5.2 隔离约定，登记入集成测试记录第 2 段与对应 §4.4 测试代码清单」；并在集成测试用例执行记录段补充非依赖类执行失败的处置路径（如按设计用例缺陷升级人工裁定制）。

### 建议级 4.2 —— §4.5「执行归属」「核验方式」字段章节锚点偏差（第 2 项 vs 第 3 项）

- **位置**：`references/testing-stage.md` §4.5（L95）；锚点对象 `references/design-stage.md` §4.8（L148-154）
- **原文摘录**：
  - testing-stage L95：「执行命令与预期结果取自设计阶段 `test-cases.md` §4.8 第 2 项（接口集成测试用例）的「核验方式」字段」
  - design-stage §4.8 第 3 项 L152：「**核验方式**（必填）：测试框架名（沿用工程既有）+ 运行命令 + 预期结果模板」
- **期望标准**：design-stage §4.8 中「核验方式」字段定义于**第 3 项「用例条目结构」**（每条 TC/TI/TE 共用），第 2 项「用例分类与编号空间」仅给出 TI-NNN 类别描述（前置条件、调用序列、预期结果、清理动作），不含「核验方式」字段定义。该引用将字段归属锚到第 2 项，与 I-6 修复的锚点精度问题同类，属 I-5 修复新增段引入的锚点偏差。
- **修改方向**：改为「……取自设计阶段 `test-cases.md`（按《设计阶段》§4.8 模板）**第 3 项「用例条目结构」**定义的「核验方式」字段（接口集成测试用例 TI-NNN 类别见第 2 项）」。

### 建议级 4.3 —— §5 图注「终止本阶段」六类情形未列 §5.1.5 测试基础就绪核验升级终止

- **位置**：`references/testing-stage.md` §5 图注（L152）；对应 §5.1.5 升级规则（L187-188）
- **原文摘录**：
  - 图注 L152：「『终止本阶段』对应六类情形：入口达上限升级后人工裁定终止、入口就绪不满足升级后人工裁定终止（§5.1）、测试基础问询升级后人工裁定终止（§5.2）、实例启动前置不满足升级后人工裁定终止（§5.4）、确认环节需求方不可达经裁决者裁定终止（§7.4）、缺陷归因升级后人工裁定终止（§7.2）」
  - §5.1.5 L187：「问询达上限 / 停滞 / 需求方不可达 → 升级人工（裁定选项：① 补齐后续流（重新问询或等待恢复）；② **终止本阶段**（决策留痕）；裁定结论登记验收核验记录人工裁定段并受 §7.4 强制确认约束）」
- **期望标准**：§5.1.5 升级规则在两个分支（问询达上限分支、基础设施缺陷分支）均提供「② 终止本阶段」，流程图亦有 `TR -.核验失败 / 问询达上限 / 不可达.-> HUM` 连线；而图注宣称「对应六类情形」未列 §5.1.5（§5.1.5 与 §5.2 为两个独立机制，不可并入 §5.2 类目）。实际终止情形为七类，图注枚举与 §5.1.5 机制口径不一致（C3 维度）。
- **修改方向**：图注六类增补「测试基础就绪核验升级后人工裁定终止（§5.1.5）」并将「六类」改为「七类」；或明确声明 §5.1.5 终止并入某一既有类目。

### 建议级 4.4 —— §5.1.5 四项依赖问询上界仅数据库项显式，token/域名/mock 依赖推断

- **位置**：`references/testing-stage.md` §5.1.5（L180-183）
- **原文摘录**：
  - L180：「**数据库**：……探查无法确定时向用户问询（问询上界与停滞规则比照《开发阶段》§5.1：默认 3 轮，达上限/停滞/不可达升级人工）」
  - L181-182：「**登录 token**：……无可用机制时向用户问询获取方式（直接登录账号 / mock 账号凭据 / 测试环境预置 token——任一即可）；**测试域名**：……无可用配置时向用户问询（测试域名 / 桩服务 / 本地启动回环地址——任一即可）」
- **期望标准**：token/测试域名（及 mock）项的问询上界与停滞规则未显式声明（「默认 3 轮」仅数据库项写明），只能经「升级规则（统一适用上述四项）」间接推断。按 C2「问询上界/停滞规则衔接一致」判据，四项应同口径显式，避免执行歧义。
- **修改方向**：在 §5.1.5「升级规则」段首补一句「各项问询上界与停滞规则统一比照《开发阶段》§5.1：默认 3 轮，达上限/停滞/不可达升级人工」，或把数据库项括号内的上界说明提取为四项共用说明。
