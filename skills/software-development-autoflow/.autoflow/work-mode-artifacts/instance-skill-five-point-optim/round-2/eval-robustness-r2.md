## 4. 逐条问题

### 问题 1（重要级）：TI 执行归属新增机制未闭环——「集成已核验」标记无载体无消费点，且与 §4.4 TI-NNN 字段存在执行边界冲突

**位置**：references/testing-stage.md §4.5 执行归属（L95）↔ §4.4 第 1 段（L84）、§5.4 任务指令表（L212-213）；references/design-stage.md §4.8 职责边界（L138）

**原文摘录**：
- testing-stage.md L95：「执行成功的 TI 所核验的接口对下游条目实例标记「集成已核验」（下游条目实例仅核验非 TI 覆盖的验收标准），执行失败的 TI 按第 3 段「依赖故障登记」升级路径处置。」
- testing-stage.md L84：「**对应设计阶段用例 ID**（TC-NNN / TI-NNN / TE-NNN，引自 `stages/201-design/test-cases.md`；测试阶段新增用例标注「测试阶段新增」）」
- testing-stage.md L212：「上游产物摘要 | 需求定稿产物中该条目的功能描述、验收标准、…+ 测试基础记录 + 开发入口确认记录（构建/启动命令）+（改动型/问题修复型）现状分析记录（摘要…）」（任务指令注入清单无集成测试记录/TI 执行结果项）
- design-stage.md L138：「**职责边界**：本节仅承担"用例设计"职责（用例标识、核验方式、依赖声明），**不涉及测试代码实现**——测试代码编写归测试阶段。」

**期望标准**：按 R4「无悬空引用（引用的章节/产物均存在且语义成立）」，I-5 要求「成功 TI 对下游标记集成已核验」应具备可追溯闭环：标记的承载载体、条目实例的消费方式、TI 测试代码的实现归属三者均须有明确定义。

**问题说明**：① 标记无登记位置——§4.5 第 2 段「集成测试用例执行记录」字段集（用例 ID/执行命令/运行结果/证据/依赖项引用）无任何「标记」字段，「集成已核验」成为悬空概念；② 消费点缺失——§5.4 任务指令「上游产物摘要」未注入 TI 执行结果，「下游条目实例仅核验非 TI 覆盖的验收标准」的义务在指令层面不可执行（条目实例无从得知哪些验收标准已被 TI 核验）；③ 执行边界冲突——执行归属规定 TI 由 Main Agent 在 §5.4 条目实例启动之前执行，而 §4.4 要求条目实例交付物测试代码清单对应「设计阶段用例 ID（含 TI-NNN）」，同时设计阶段明确「不涉及测试代码实现」、条目实例尚未启动——TI 测试代码由谁实现无归属，存在双重执行或漏核验的分歧；④ 工程实现缺陷经 §7.2 回退修复后，流程图 DEV 复验回边仅指向 TN（条目实例），失败 TI 的重跑时机未显式锚定（§4.5 对应关系段仅言「再重跑」）。

**修改方向**：
1. §4.5 第 2 段「集成测试用例执行记录」增「下游标记」字段（运行结果=通过时登记「集成已核验」+ 覆盖接口/验收标准范围）；
2. §5.4 任务指令「上游产物摘要」增「集成测试记录执行结果摘要（已核验 TI-NNN 列表）」注入项；
3. 明确 TI 测试代码实现归属：「核验方式」命令依赖工程既有代码则直接执行；代码缺失时由 Main Agent 依 §5.2 测试基础编写并登记，或升级人工裁定；
4. 明确失败 TI 在 §7.2 回退修复后的重跑时机（修复定稿 + 闸门重跑后由 Main Agent 重新执行并回写第 2 段，再进入条目实例编排）。

### 问题 2（建议级）：「执行归属」引用「§4.8 第 2 项…「核验方式」字段」锚点不准

**位置**：references/testing-stage.md §4.5（L95）；references/design-stage.md §4.8（L143、L148-152）

**原文摘录**：
- testing-stage.md L95：「执行命令与预期结果取自设计阶段 `test-cases.md` §4.8 第 2 项（接口集成测试用例）的「核验方式」字段」
- design-stage.md L143：「2. **用例分类与编号空间**：…**接口集成测试用例 TI-NNN**（独立编号空间）：…用例描述含**前置条件**（数据库 schema / 登录 token / 测试域名等依赖）、调用序列、预期结果、清理动作」
- design-stage.md L148：「3. **用例条目结构**（每条 TC/TI/TE 共用）：…**核验方式**（必填）：测试框架名（沿用工程既有）+ 运行命令 + 预期结果模板」

**期望标准**：引用锚点与模板结构逐项对应（本实例 r1 已就同类锚点问题提出 I-6 并修复，锚点精度属既有质量底线）。

**问题说明**：「核验方式」字段定义于第 3 项「用例条目结构」；第 2 项仅给出 TI-NNN 类别描述（前置条件/调用序列/预期结果/清理动作），不含「核验方式」字段——该引用指向的「第 2 项…的核验方式字段」组合在模板中不存在，为 I-5 修复新引入的锚点失准。

**修改方向**：改为「§4.8 第 3 项（用例条目结构）的「核验方式」字段」。

### 问题 3（建议级）：基础设施缺陷升级选项「重新进入入口判定」与流程图 HUM 回边及同节统一升级规则表述不一致

**位置**：references/testing-stage.md §4.5 第 3 段（L110）、§5.1.5 升级规则（L187-188）↔ §5 流程图（L132-133）

**原文摘录**：
- L110：「基础设施缺陷（数据库 / 测试域名 / mock 不可用）：升级人工（裁定选项：① 补齐基础设施依赖后可重新进入入口判定；② **终止本阶段**——决策留痕；裁定登记验收核验记录人工裁定段并受 §7.4 强制确认约束）」
- L188：「基础设施缺陷升级人工（裁定选项：① 补齐基础设施依赖后可重新进入入口判定；② **终止本阶段**——决策留痕…）」
- L132-133：「TR -.核验失败 / 问询达上限 / 不可达.-> HUM」「HUM -.依赖项补齐续流.-> TR」
- L187：「问询达上限 / 停滞 / 需求方不可达 → 升级人工（裁定选项：① 补齐后续流（重新问询或等待恢复）；② **终止本阶段**…）」

**期望标准**：同一升级人工裁定点的续流语义应与流程图边及同节规则一致（R2「处置路径可追溯」；I-3 修复要求与 §5 流程图 HUM 边衔接）。

**问题说明**：基础设施缺陷在 §5.1.5 就绪核验阶段暴露，其恢复续流应为回到 TR 重新就绪核验（图中专设「依赖项补齐续流」回边）；而 I-3 修复选用的措辞「重新进入入口判定」在本章专指 `HUM -.重新进入入口判定.-> G0` 边（§5 入口条件段、§5.1 就绪核验段均以此指代 G0 边），语义指向入口条件判定（不核验依赖项），与 TR 回边错位；同一裁定点同时存在「补齐后续流（重新问询或等待恢复）」与「重新进入入口判定」两种续流表述。功能上经 G0→TP→TR 仍可收敛，但指令语义含混、可追溯性受损。两处文本（L110/L188）之间口径一致，问题在于与图边及统一规则的衔接。

**修改方向**：统一为「补齐基础设施依赖后重新进入 §5.1.5 就绪核验（图中 `HUM -.依赖项补齐续流.-> TR`）」，或显式说明与 G0 边「重新进入入口判定」的关系。
