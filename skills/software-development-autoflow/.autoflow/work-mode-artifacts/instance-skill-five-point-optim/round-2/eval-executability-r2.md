## 3. 收敛建议及依据

**不建议收敛。**

- 实质依据：I-5 修复虽闭合 r1 的执行归属模糊问题，但**引入了 3 条重要级执行链缺口**（TI 测试代码编写归属未定义；「集成已核验」标记无下游消费钩子；TI 失败修复后重跑闭环断裂），另含 1 条建议级锚点偏移（「§4.8 第 2 项…核验方式」字段实际位于第 3 项）。修复闭合性核验结论为 **I-5 部分闭合**，指令可执行性未达满分锚定（"无需推断即可执行"）；

## 4. 逐条问题

### 重要级（3 条，均为 I-5 修复引入的新问题）

#### 4.1 TI-NNN 测试代码编写归属未定义

- **位置**：testing-stage.md §4.5 执行归属（L95）；对照 §3「测试代码即产物」（L47）、design-stage.md §4.8 职责边界（L138）
- **原文摘录**：
  - L95：「TI-NNN 用例（接口集成测试）由 **Main Agent（编排者）** 在 §5.1.5 测试基础就绪核验通过后、§5.4 条目实例启动**之前**，以阶段层任务一次性执行（不分配至条目实例——TI 可能跨 REQ-NNN）；执行命令与预期结果取自设计阶段 `test-cases.md` §4.8 第 2 项（接口集成测试用例）的「核验方式」字段」
  - L47：「测试实例的执行者直接在工作空间工程内编写测试代码（测试脚本、用例、共享 fixture）」——"测试实例"=§5.4 条目实例
  - design-stage §4.8 L138：「**不涉及测试代码实现**——测试代码编写归测试阶段」
- **问题**：TI 在条目实例启动之前由 Main Agent 执行，但执行所依赖的测试代码（核验方式=测试框架名+运行命令，需代码文件存在）无编写归属——Main Agent 实例外职责枚举（§5.1/§5.1.5/§5.2/§5.5：核验、问询、登记、建立、归因）不含"编写测试代码"；条目实例执行者此时尚未启动。且 §4.4 测试代码清单为条目实例交付物字段，TI 代码（跨 REQ-NNN）无登记载体。执行者必须自行推断 TI 代码来源。
- **期望标准**：E1 满分锚定"无需推断即可执行"——TI 代码编写者、时点、落盘位置应有明确定义。
- **修改方向**：在 §4.5 执行归属段补"TI 测试代码由 Main Agent 于 §5.1.5 通过后按 §4.8 核验方式字段建立，落盘登记入 §4.5 第 4 段测试环境声明（或测试基础记录）"；或在 §5.2 测试基础设施前置职责中增"TI 测试代码建立"项。

#### 4.2 「集成已核验」标记无下游消费钩子

- **位置**：testing-stage.md §4.5 执行归属（L95）；对照 §5.4 任务指令表（L213）、§4.3 验收核验记录（L78）、§4.4 测试代码清单（L84）
- **原文摘录**：
  - L95：「执行成功的 TI 所核验的接口对下游条目实例标记「集成已核验」（下游条目实例仅核验非 TI 覆盖的验收标准）」
  - L213（§5.4 任务指令·上游产物摘要）：「需求定稿产物中该条目的功能描述、验收标准、（关联时）回归边界条目 + 该条目关联任务的开发交付物摘要（经任务清单关联定位）+ 测试基础记录 + 开发入口确认记录（构建/启动命令）+（改动型/问题修复型）现状分析记录」——无 TI 执行结果/已核验接口列表注入项
  - L78（§4.3）：核验方式取值仅「自动化测试 / 人工核验」；L84（§4.4）：测试代码清单字段无"TI 已核验免验"声明
- **问题**：标记机制声明了但无传递与登记载体——条目实例无法获知哪些接口已被 TI 核验（任务指令注入表无对应项，跨阶段自行读取违反 §3 注入纪律）；验收核验记录按 REQ-NNN 逐条登记，TI 覆盖条目的结论由谁、以何种核验方式登记未定义；§5.5 出口判定①「验收标准全部核验（验收核验记录逐条有结论与证据）」在条目实例跳过 TI 覆盖标准后无法满足。"下游条目实例仅核验非 TI 覆盖的验收标准"不可执行。
- **期望标准**：标记的注入路径、登记口径、出口判定衔接三点闭合。
- **修改方向**：① §5.4 任务指令"上游产物摘要"增"集成已核验接口列表（引自 §4.5 第 2 段执行记录，Main Agent 注入）"；② §4.3 核验方式枚举增「集成已核验（引用 TI-NNN 执行记录）」取值。

#### 4.3 TI 执行失败（工程实现缺陷类）的修复后重跑路径未定义

- **位置**：testing-stage.md §4.5 第 3 段（L109-111）；对照 §5.5 修复回退与复验（L249）
- **原文摘录**：
  - L111：「工程实现缺陷：按缺陷回退 §7.2 处置（关联任务条目 ID 后经开发阶段缺陷修复回退通道重新激活对应任务实例）」
  - L249：「修复定稿且闸门通过后，Main Agent 以缺陷复验为追加约束重启受影响测试实例」——复验机制面向"受影响测试实例"（§5.4 条目实例）
- **问题**：TI 为阶段层任务（非实例），在条目实例启动前执行。若 TI 因工程实现缺陷失败，按 §7.2 回退开发修复后，TI 重跑由谁触发、以什么机制、何时执行（条目实例启动前补跑 / 随条目实例并行？）均无定义；§7.2/§5.5 的"重启受影响测试实例"复验语义不适用于阶段层 TI。执行失败路径闭环断裂，与 §4.5 执行归属"执行失败的 TI 按第 3 段升级路径处置"的衔接不成立。
- **期望标准**：每类故障均有终态（R2 锚定）——工程实现缺陷类 TI 失败须有修复后重跑的触发、机制、时点定义。
- **修改方向**：§4.5 第 3 段工程实现缺陷处置路径补"修复定稿且闸门通过后，由 Main Agent 重跑受影响 TI-NNN 并登记第 2 段，全部通过后方可启动条目实例"；或在 §5.5 修复回退段增 TI 阶段层复验子句。
