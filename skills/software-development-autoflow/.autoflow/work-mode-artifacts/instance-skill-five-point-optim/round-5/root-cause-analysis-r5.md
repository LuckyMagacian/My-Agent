# 根因分析：台账指针不完整为何反复出现（root-cause-analysis-r5）

> 实例：instance-skill-five-point-optim ｜ 触发：用户指令「修复 J-7，但需要分析为何该问题多次出现，是否可能是因为多度设计」
> 分析对象：version-evolution §4 版本总账指针不完整问题（4 次出现，贯穿 r2~r5）
> 依据：issue-log 台账（R2-2 / R3-1 / R4-1 / R5-1）、changelog 07/10/11/12 明细、arbitration-r2~r5 记录

## 1. 复发谱系——四次出现的形态差异

| 轮次 | 问题 | 形态 | 具体表现 |
| --- | --- | --- | --- |
| r2 | J-2（R2-2） | **错指针**（抄错值） | 总账行指针与 changelog 条目错位——context 行「23」（实为交叉引用条目）、testing 行「25」为本批新增错值；另有 5 行既有错位；「方案优化文档」行整体缺失 |
| r3 | J-5（R3-1） | **零指针**（整体跳过） | 当日修复批次 7 条目对总账零登记；机制修订自标「不升版」违反 version-evolution §2.2 |
| r4 | J-6（R4-1） | **漏行**（枚举遗漏） | 总账 2026-08-12 延展清单漏「交叉引用索引（工具文件）」行（条目 12 声称清单与落地不一致） |
| r5 | J-7（R5-1） | **漏条目**（历史批次口径不一致） | 08-10 批次延展漏 7 条目跨 5 行——交叉引用索引行缺 08-10 末次校验指针（条目 8、18）、testing 行缺条目 3、16、development 行缺条目 4、design 行缺条目 5、context 行缺条目 6；同批内 SKILL 行条目 2（仅元数据）已登记、其余被漏 |

**形态各异的四次失败，指向同一根因**：台账登记依赖人工逐条枚举，且登记粒度细则在历次评估中不断叠加。四次不是四个独立缺陷，而是同一失效模式（手工逐条登记不可靠）的四种表现。

## 2. 三层根因

### 直接层：逐条目手工枚举不可靠

- 每次升版批次需核对：changelog 当日全部条目 ↔ 总账每行 ↔ §2.4 七处引用侧同步项，全部为手工比对，无任何机器可执行校验。
- 错值（J-2）、整体跳过（J-5）、漏行（J-6）、漏条目（J-7）都是同一手工枚举失误的不同表现——纠错一轮只是把错值改对、把漏项补上，**枚举方式本身没有改变，因此必然复发**。

### 机制层：总账是 changelog 的冗余派生索引 + 登记规则叠加

- 总账本质是 changelog 的**派生索引**（§4「轻量指针表，不双写」——不承载任何 changelog 之外的新信息，纯指针）。
- 派生索引的可靠性完全取决于登记时的枚举完整性，而登记粒度细则在历轮评估中被不断叠加：
  1. 机制变更登记（基本义务）；
  2. **不升版亦登记**（r3 J-5 修复确立——仅元数据同步也要登记）；
  3. **当日多次更新登记当日粗粒度指针**（r4 J-6 修复沿用——「末次校验行更新」）；
  4. 建立事件登记（目录/工具文件）；
  5. 本文行不累积自身指针、changelog 目录行只记建立事件（r3 条目 12 确立的例外）；
  6. 仅元数据须显式标注。
- 规则越多，每次登记的决策分支越多、遗漏面越大。r3 修复「不升版亦登记」后，登记义务扩大（每个仅元数据条目都要登），直接放大 r4/r5 两轮出现漏行、漏条目的概率。

### 设计层：过度设计信号（部分成立）

对比证据（本实例内天然对照实验）：

| 行类型 | 登记粒度 | 3 次延展（08-10/08-11/08-12）错误数 |
| --- | --- | --- |
| 交叉引用索引行 | **按日粗粒度指针**（「末次校验行更新」，不枚举条目） | **0** |
| testing/development/design/context 等行 | **逐条目枚举**（「条目 N、M（仅元数据同步）」） | **4**（J-2/J-5/J-6/J-7 全部落在逐条目枚举行或批次内） |

- 08-10 批次是同批内口径不一致（SKILL 行条目 2 登记了、其余 7 条目漏了）——不是规则缺失，是**逐条目枚举在执行中不可靠**。
- 08-07 同日多条目（条目 9/12/15 末次校验更新）由「条目 2（建立事件）」粗粒度指针覆盖，历轮零问题——再次支持粗粒度指针的可靠性。

## 3. 过度设计判定

**部分成立**：

- **轻量指针表本身合理**（跨文件追溯链需要索引；changelog 按日归档合理）——不属过度设计。
- **过度设计的是登记粒度**：逐条目（乃至逐字段级）登记粒度超出人工维护的可靠边界；总账行的价值是「指向当日明细」，不是「复述当日明细」（§2.3 本已声明「不复述细节」——但登记粒度实际走到了接近复述细节的程度，与自身定位矛盾）。
- **规则叠加放大了粒度成本**：6 条登记细则 × 每次升版 9~10 行 → 每次批次约 40~70 个手工登记决策点，零失误不现实。r3 的「不升版亦登记」在方向上正确（堵住了零登记漏洞），但把义务推到逐条目粒度，反而把漏洞从「漏整日」转变为「漏条目」。

## 4. 熔断处置（work-mode §6 同根因复发熔断）

本问题已达同根因第 4 次出现，**触发熔断：禁止再加守卫**（不加检查清单、不加流程步骤、不加登记字段——任何新增守卫都是第 5 次失败的铺垫）。正确响应只有两条路：

1. **模型级修复（零机制改动）**：执行者升版登记时按「行 → 日 → 条目」两级核验——先核对总账每一行覆盖了当日的哪几天（行级粗核），再核对当日 changelog 的每个条目在对应行有落点（条目级细核，仅对当日批次）；
2. **减法轮简化（需独立评估轮次）**：将总账登记粒度从「逐条目」降为「按日粗粒度指针」（与交叉引用索引行同型，如「changelog/2026-08-10.md：当日全部条目」或仅「当日批次已登记」），细节完全交给 changelog 明细——机制修订须经 work-mode 独立评估轮次实施，**不在本实例内单方实施**。

## 5. 结论

- 台账指针不完整 4 次复发的直接原因是**手工逐条目枚举不可靠**；机制原因是**派生索引 + 登记规则叠加**；设计原因是**部分过度设计**——粒度过细（逐条目），而非指针表本体。
- 证据最强的信号：**粗粒度行零错误 vs 细粒度行 4 错误**（同文件、同批次、同时期），指向粒度过细是唯一稳定的错误源。
- 处置遵循熔断：不加守卫；二选一——模型级执行纪律（立即可行）/ 减法轮简化登记粒度（机制修订，独立评估）。
