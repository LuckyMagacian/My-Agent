#### I-1（跨视角：governance G1 + maintainability M2）三阶段细则头部对齐基准残留旧版本号

- **根因标签**：版本同步遗漏（引用侧同步）
- **严重程度**：重要级
- **发现视角**：governance、maintainability
- **位置**：`references/requirements-stage.md` L6、`references/development-stage.md` L6、`references/testing-stage.md` L8
- **原文**（以 requirements-stage.md 为例）：
  ```
  > 对齐基准：`work-mode.md` v1.9；`context-system.md` v2.3.6；`design-stage.md` v0.9.4；`development-stage.md` v1.3；`testing-stage.md` v1.3
  ```
- **现状**：context-system 现行 v2.3.7（已从 v2.3.5→v2.3.6→v2.3.7），design-stage 现行 v0.9.5（已从 v0.9.2→v0.9.3→v0.9.5）。三处「对齐基准」行仍引用旧版本 v2.3.6 / v0.9.4，属被评批次自身改动未完成跨组件同步（diff 确认这些行在本批改动中已被修改但写入了错误的目标版本）。
- **期望标准**：三段对齐基准行应更新为 context-system v2.3.7、design-stage v0.9.5。
- **修改方向**：三文件各 1 行版本号修正。

#### I-2（convergence C2/C3）§7.4 强制确认锚点显式枚举遗漏 §5.1.5 测试基础就绪核验裁定

- **根因标签**：枚举遗漏
- **严重程度**：重要级
- **发现视角**：convergence
- **位置**：`references/testing-stage.md` §7.4 通用规则·强制确认（L323）；对照 §4.3 人工裁定段来源枚举（L78）、§5.1.5 升级规则（L184）
- **原文**（L323）：
  ```
  **强制确认**：触发锚点为**验收核验记录中未经需求方确认的人工裁定记录**，显式枚举全部来源：入口条件（G0）升级裁定、§5.1 就绪核验裁定、§5.2 测试基础问询裁定、§5.5 缺陷归因裁定、§7.2 缺陷接受/转出裁定、§7.3 迭代期裁定；
  ```
- **问题**：§5.1.5 测试基础就绪核验升级规则声称「裁定登记验收核验记录并受 §7.4 强制确认约束」，但 §7.4 显式枚举缺「§5.1.5 测试基础就绪核验裁定」；§4.3 人工裁定段来源枚举已同步为「F-4 本批同步」，与 §7.4 枚举（未同步）口径矛盾。同一裁定来源三处口径不一致（§4.3「已同步」、§5.1.5「声称受约束」、§7.4「未枚举」），确认闭环断裂。
- **期望标准**：§7.4 枚举补全「§5.1.5 测试基础就绪核验裁定」，三处口径一致。
- **修改方向**：testing-stage.md §7.4 枚举列表增 1 项。

#### I-3（跨视角：convergence C3 + robustness R2）基础设施缺陷处置路径引用不存在的「工程环境就绪」问询机制

- **根因标签**：悬空引用
- **严重程度**：重要级
- **发现视角**：convergence、robustness
- **位置**：`references/testing-stage.md` §4.5 第 3 段·处置路径（L108）与 §5.1.5 升级规则（L185）
- **原文**（L108）：
  ```
  基础设施缺陷（数据库 / 测试域名 / mock 不可用）：退回上游「工程环境就绪」问询（升级人工，参照 §5 入口条件升级规则）；
  ```
- **问题**：全工作区核验（grep）未找到「工程环境就绪」问询的定义或所在地——既非现有问询标题也非 §5 入口条件段落标题。基础设施不可用的处置路径指向不存在的机制，故障处置闭环在此处断裂。
- **期望标准**：基础设施缺陷应要么引用一个已定义的问询机制（如开发阶段 §5.1 工作空间工程确认），要么直接升级人工（比照设计用例缺陷路径「升级人工—来源标注」），不得引用不存在的机制。
- **修改方向**：替换「工程环境就绪」为实际存在的问询引用或直接升级人工路径。

#### I-4（convergence C1）test-cases.md「入口必备」缺少 G0 与 §5.1 的可执行核验落点

- **根因标签**：入口条件缺核验执行点
- **严重程度**：重要级
- **发现视角**：convergence
- **位置**：`references/testing-stage.md` §5 入口条件（L156）、§5.1 入口就绪核验（L164-167）；对照 §3 输入②（L42）与流程图 IN 节点（L122）
- **原文**（L42）：
  ```
  ② **设计阶段测试用例设计产物** `stages/201-design/test-cases.md`（《设计阶段》§4.8，**入口必备**——未生成或未定稿时测试阶段入口条件不满足，回退上游或升级人工）；
  ```
- **问题**：「入口必备」在 §3 输入表声明了回退/升级规则，流程图有 IN 节点，但 §5 G0 规范定义段落与 §5.1 入口就绪核验四项中均无 test-cases.md 的核验落点。test-cases 作为入口条件仅有声明无执行，前置未满足仍可能启动测试阶段（声明型实际不可执行）。
- **期望标准**：§5 G0 应含 test-cases.md 入口条件声明，或 §5.1 新增一项核验落点（与四项依赖项就绪核验并列或以 §5.1 前哨段明确定义核验时机与路径）。
- **修改方向**：testing-stage.md §5 G0 或 §5.1 补 test-cases.md 核验落点。

#### I-5（executability E3）TI-NNN 集成测试用例执行主体与时机未定义

- **根因标签**：执行主体未定义
- **严重程度**：重要级
- **发现视角**：executability
- **位置**：`references/testing-stage.md` §4.5 接口集成测试记录模板（L85-L120）、§5 执行流程图（L180-L308）；`references/design-stage.md` §4.8 第 2 项（L143）
- **原文**（§4.5 目录 L85）：
  ```
  ### 4.5 接口集成测试记录
  ```
- **问题**：TI-NNN 用例（接口集成测试）在设计阶段 §4.8 定义，测试阶段 §4.5 记录执行结果，但两阶段间无明确的「执行归属」定义——是哪个 phase 的哪个 instance 负责执行 TI-NNN？测试阶段流程图包含测试实现/缺陷登记/回归测试/验收，但无集成测试执行节点（§5 中 T1 仅指普通测试实例，无对应 TI 执行实例类型）。依赖项就绪核验（§5.1.5）和集成测试记录记录的是就绪状态与运行结果，但「谁去运行这些依存于数据库/token/域名的跨接口用例」不受定义，多个 TI 可能跨多 REQ-NNN 但 instance 映射为 1:1。
- **期望标准**：TI-NNN 的执行归属应显式定义：可由测试阶段实例化一个集成测试子实例（TI-N 入口实例），或作为测试实例内的执行步骤（如测试实现阶段的一个子步骤），或升级人工指定。三种路径择一。
- **修改方向**：testing-stage.md §5 流程图或 §4.5 头段增 TI-NNN 执行归属定义。

#### I-6（executability E3 + convergence C1）design-stage §4.8 两处引用锚点错位

- **根因标签**：引用锚点错位
- **严重程度**：重要级
- **发现视角**：convergence、executability
- **位置**：`references/design-stage.md` §4.8 第 3 项（L154：「引自第 5 段依赖声明」）、§4.8 强制路径（L166：「测试阶段 §3 输入①」）
- **原文**（L154）：
  ```
  - **依赖引用**（TI/TE 必填）：引自第 5 段依赖声明的具体项；
  ```
  对照 §4.8 模板实际结构：第 6 项为「依赖声明」，非第 5 项。
- **问题**：模板第 5 项为「接口覆盖核对表」、第 6 项为「依赖声明」——「第 5 段」为优化日志旧模板序号残留。同理，L166 「测试阶段 §3 输入①」实际应为输入②（输入①为验收标准，输入②为 test-cases.md）。两处错位属本批新增模块的序号修正常见遗留。
- **期望标准**：L154 改为「引自第 6 段依赖声明」；L166 改为「测试阶段 §3 输入②」。
- **修改方向**：design-stage.md §4.8 两处数字修正。
