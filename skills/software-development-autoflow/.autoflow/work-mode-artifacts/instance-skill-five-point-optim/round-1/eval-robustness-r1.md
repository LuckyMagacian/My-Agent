## 4. 逐条问题

### 问题 1（重要级）—— 基础设施缺陷处置路径引用未定义问询「工程环境就绪」，处置路径不可追溯

- **位置**：`references/testing-stage.md` §4.5 第 3 段（第 108 行）；同 §5.1.5 升级规则（第 185 行）
- **原文摘录**：
  - 「基础设施缺陷（数据库 / 测试域名 / mock 不可用）：退回上游「工程环境就绪」问询（升级人工，参照 §5 入口条件升级规则）；」
  - 「核验失败的依赖项：登记入 §4.5 第 3 段「依赖故障登记」——按故障类别……基础设施缺陷退回上游「工程环境就绪」问询（升级人工），工程实现缺陷按 §7.2 缺陷回退处置，设计用例缺陷升级人工裁定制；」
- **期望标准**：R2 锚定「处置路径可追溯」。处置路径引用的上游问询须有既有定义或在本批显式定义。经全工作区检索，「工程环境就绪」仅出现在 testing-stage 上述两处自引用中；上游最接近的定义为《开发阶段》§5.1「工作空间工程确认」（"向用户确认是否已将全部相关工程加入工作空间"）与「构建/启动命令登记」，名称与语义均不对应；SKILL.md §9 人工介入点索引亦无此项。执行者无法确定"退回上游"到哪个阶段、执行哪一问询。
- **修改方向**：① 将「工程环境就绪」显式映射为既有问询并改写引用，如"退回上游《开发阶段》§5.1 入口准备（工作空间工程确认 + 构建/启动命令登记）问询"；或 ② 在 testing-stage 本批显式定义该问询（问询内容、上界、登记载体），并同步登记 SKILL.md §9 人工介入点索引。

### 问题 2（建议级）—— design-stage §4.8 测试用例设计模板两处内部引用错位（悬空引用）

- **位置**：`references/design-stage.md` §4.8 第 3 项（第 154 行）与 §4.8 强制路径（第 166 行）
- **原文摘录**：
  - 「**依赖引用**（TI/TE 必填）：引自第 5 段依赖声明的具体项；」
  - 「**强制路径**：本节产物是测试阶段 §3 输入①的入口必备项（测试阶段消费，见《测试阶段》§3）……」
- **期望标准**：R4 无悬空引用——引用锚点与实际结构一致。核对事实：§4.8 第 5 段为「接口覆盖核对表」，依赖声明实为第 6 段（"6. **依赖声明**（关键，测试阶段入口必备）……"）；《测试阶段》§3 输入表中 test-cases 为**输入②**（"输入 | ① 开发出口产物……；② **设计阶段测试用例设计产物** `stages/201-design/test-cases.md`……"），输入①为开发出口产物。两处错位均由 v0.9.3 新增 §4.8 时模板结构演进（插入"用例条目结构"、输入编号调整）后未同步内部引用所致；testing-stage §4.5/§5.1.5 侧引用（"《设计阶段》§4.8 第 6 段"）是正确的，反证错位在 §4.8 自身。
- **修改方向**：「第 5 段依赖声明」→「第 6 段依赖声明」；「§3 输入①」→「§3 输入②」。

### 问题 3（建议级）—— 依赖故障「升级方向」三选一的判定准则未显式化，同类症状可归入不同处置路径

- **位置**：`references/testing-stage.md` §4.5 第 3 段（第 107~110 行）；§5.1.5 升级规则（第 185 行）
- **原文摘录**：
  - 「3. **依赖故障登记**（核验失败或执行阻塞时按故障类别登记）：故障 ID、故障类别（数据库 / token / 测试域名 / 第三方 mock）、影响范围（阻塞的 TI-NNN 列表）、升级方向（设计用例缺陷 / 工程实现缺陷 / 基础设施缺陷）、处置路径：」
- **期望标准**：R2 每类故障均有终态且路径可执行。当前同一故障症状可对应多个升级方向（如"数据库未就绪"既可能是基础设施缺陷——无数据库服务/未预置，也可能是工程实现缺陷——迁移脚本错误，还可能是设计用例缺陷——声明的 schema 路径错误），而三类处置路径分叉明显（退回上游问询 / §7.2 缺陷回退 / 升级人工修正用例），判定准则缺失将导致归类依赖 Main Agent 自行推断，同类故障在不同需求上可能走不同路径。
- **修改方向**：在 §5.1.5 升级规则或 §4.5 第 3 段增补判定判据（如：依赖声明与工程实际不符→设计用例缺陷；工程内脚本/配置可定位错误→工程实现缺陷；外部设施缺失/不可达→基础设施缺陷），并补兜底条款"无法判定时升级人工归因，裁定登记验收核验记录人工裁定段"。

### 问题 4（建议级）—— TI-NNN 集成测试用例的执行归属未锚定，故障登记闭环依赖的执行行为无流程节点承载

- **位置**：`references/testing-stage.md` §4.5（第 93~106 行）；§5 执行流程图（第 120~148 行）；`references/design-stage.md` §4.8 第 3 项（第 150 行）
- **原文摘录**：
  - 「由 Main Agent 在测试运行阶段就绪核验（§5.1+§5.2 之间新增段）通过后登记维护，记录**接口集成测试**（TI-NNN 编号空间）的依赖项就绪核验、用例执行结果与环境声明」；「2. **集成测试用例执行记录**：每用例（TI-NNN）逐条记录——**执行命令**……**运行结果**（通过 / 失败 / 阻塞）」
  - 「**关联 REQ-NNN**（必填，多条时全列）；」（TI 用例可跨多条需求条目）
- **期望标准**：R1 覆盖充分且无未定义分支。§4.5 的"执行记录"隐含集成测试执行行为的存在，但流程图自 TR（§5.1.5 就绪核验）直接进入 TI（§5.2 基础设施前置）→ TN（条目测试实例并行），无集成测试执行节点；结合 §3 归档约定"测试条目与实例 1:1"与 TI 用例可关联多条 REQ-NNN 的结构，TI 用例由哪个（些）实例、在何时执行存在归属歧义——多条目关联的 TI 用例无唯一归属实例。
- **修改方向**：在 §4.5 或 §5 流程图显式声明执行归属，如"TI-NNN 用例由关联条目测试实例（TN）执行、跨条目的 TI 由 Main Agent 在 §5.2 之后统一执行，执行结果由 Main Agent 汇总登记入 §4.5 第 2 段"。

### 问题 5（建议级）—— 软链接机制无跨平台声明（macOS/Linux 透明、Windows 处置说明缺失）

- **位置**：`references/context-system.md` §11.10（第 401 行）；§4 docs/ 软链接集合新增行（第 116、119、120 行）；`references/testing-stage.md` §3 归档约定（第 45 行）
- **原文摘录**：
  - 「10. **软链接一致性**：`docs/` 软链接集合（§4 目录布局）的链接目标须真实存在；阶段定稿时由 Main Agent 在写入交付物后**同批创建**软链接；阶段未启动时软链接不创建（不预创建悬空链接）；需求结束（§10 归档只读）时软链接随目录转只读——断点恢复（§9.3）时若发现悬空软链接，按"链接目标缺失"登记阻塞项，修复路径二选一：补全缺失交付物后重建链接，或撤销悬空软链接并留痕。」
- **期望标准**：R3 锚定「symlink 跨平台声明（macOS/Linux 透明、Windows 说明）」。经全工作区检索，所有软链接条款（§11.10、§4 布局行、四份阶段细则归档约定）均无平台声明；本批新增的 `test-cases.md` / `integration-test-record.md` / `acceptance-verification.md` 软链接创建动作延续了该机制。Windows 环境（符号链接需开发者模式或提升权限）下本批新增的创建义务无处置条款。（机制本体源于前批 v2.3.5，本批为扩展面，故列建议级。）
- **修改方向**：§11.10 增一句跨平台说明，如"macOS/Linux 下软链接透明可用；Windows 环境需开发者模式，链接创建失败时按悬空链接处置路径登记并留痕"。

### 问题 6（建议级）—— 新编号阶段目录方案无"存量归档兼容"声明（只对新启动需求生效）

- **位置**：`references/context-system.md` §4 目录布局树（第 108~156 行）
- **原文摘录**：
