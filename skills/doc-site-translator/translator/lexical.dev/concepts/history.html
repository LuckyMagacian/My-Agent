useHistory

Lexical 的 useHistory 添加了对 Undo 和 Redo 的支持。撤销和重做的一部分需要支持某些动态操作的合并，例如连续输入。下面提供了有关连续输入撤销合并功能的背景信息。

输入文本的 Undo Coalescing #

TL;DR：在使用文本编辑器时，用户期望一个精心打磨的撤销体验。关键部分是在撤销连续输入事件时有流畅、深思熟虑的工作流程。对于本文，严格输入事件可能仅限于输入字符、退格和向前删除。用户通常期望连续输入可以通过单个撤销手势完全撤销，而不需要为每个字符单独的撤销手势。涵盖此内容的算法是"输入文本的撤销合并"，其中涉及一定程度的细微差别。本文涵盖了这些细微差别，同时避免规定性的实现细节。

什么类型的编辑需要 Coalescing？

如上所述，连续输入应该合并为单个撤销操作。连续输入是一个复杂的短语，我们将在下面讨论一些细节。还有其他类型的编辑需要撤销合并，例如快速调整图片大小或快速更改所选文本的字体大小。后两个例子属于可能被称为"动态操作"的类型，它们的实现可能与输入合并有很大不同。

什么构成连续输入？

为了撤销合并的目的，连续输入事件可以安全地限于这三个操作：

  • 向前输入字符（注意，稍后讨论组合字符输入）。
  • 向后删除，例如退格手势，包括退格键按下。
  • 向前删除，例如向前删除手势，包括 Delete 键按下。

以上任何中断都会破坏连续输入的概念。请注意，在这三个操作之间切换本身可能被视为连续输入的中断，也可能不是。这最终是一个可用性决策。在我看来，在检查各种文字处理器时，在这三个操作之间切换应该保持连续性，因为用户经常在输入流程中犯拼写错误或进行更正，因此倾向于将整个输入、退格和删除序列视为单个可撤销会话。请注意，Google Docs 和 Quip 将在输入、退格和删除之间切换视为对连续输入会话的干扰。

以选中文本开始，然后输入

让我们从一些选中的文本开始。用户可能直接选择了文本，可能是粘贴文本的结果，或通过其他步骤序列。当随后是连续输入时，初始选择应该与后续输入事件一起作为单个合并撤销会话的一部分。

Timeouts（超时）

文本编辑通常是一种无模式的用户体验，因此几乎任何超出上述输入操作的事件都会中断连续输入。首先是超时。Quip 似乎要求连续输入在 1 秒间隔内发生，而 Google Docs 要求约 2 秒。在我看来，超时可能延长到 3 到 5 秒。输入事件之间的时间越多，用户就越有可能有意输入一个文本块、一个想法或概念。使用超时不一定需要，时间长短当然值得讨论。协作共同编辑也使用超时来分组跨客户端合并的文本。较长的超时往往使协作成为更流畅、更少干扰的体验，因为接收其他客户端输入同时表达自己的想法往往是无益的。实现者应根据其客户期望和可能共享此超时的相关协作功能考虑正确的超时。

硬回车和软回车

按 Return 键生成的硬回车往往会中断并因此重置连续输入。对于 Google Docs 和 Quip，按 shift+Return 键生成的软回车不会终止连续输入。这是合理的，因为软回车结束文本换行但不结束段落。

更改 Selection 和键盘焦点

用户对 selection 的任何更改都应终止合并。这包括：

  • 箭头手势导航。
  • 选择单词、句子或段落的手势。
  • 任何其他不通过上述输入事件将闪烁光标移动到下一个或上一个字符的 selection 更改。

此外，结束编辑窗口上的键盘焦点，包括将焦点移动到另一个编辑窗口或同一窗口内的不同视图，也应该终止合并。这还包括将焦点设置为模态弹出窗口，例如超链接属性编辑器。

组合字符

输入变音符号、CJK 甚至 emoji 时会发生字符组合。该过程通常至少涉及这三个阶段：

  • 开始组合。
  • 用其他文本替换组合文本并继续组合。此步骤可能在单个组合会话中发生多次。
  • 停止组合，要么通过接受文本，要么通过取消最新输入。

合并应该在开始组合时终止。替换组合文本通常应该合并。停止组合可能会也可能不会重置合并，具体取决于实现。Quip 似乎尝试合并多个组合字符，但在组合和非组合字符之间切换时会中断合并。Google Docs 似乎更频繁地中断合并。两者都合并文本替换。

自动更正、拼写更正和文本替换

文本替换的行为类似于组合字符。当文本被转换时，合并应该终止，转换后的文本成为下一个撤销会话中的第一个合并条目。

复制和粘贴

任何像复制和粘贴这样的操作通常会触发不属于上述三个连续输入操作的事件。因此，复制和粘贴也会终止合并。

结论

文本撤销合并大大提高了撤销的可用性，因为它允许用户绕过在段落内形成或重新形成文本所涉及的所有中间事件。鉴于文本编辑的无模式性质，将连续输入严格限制为三个事件可以实现健壮且清晰的实现。实现者需要严格的瓶颈来捕获 selection 更改、键盘焦点更改以及来自协作客户端的更改。虽然以上内容并不完整，但我希望读者会发现它有帮助。

为内存和长时间会话调整 HistoryExtension #

HistoryExtension 附带的配置值是为富交互表面上短期编辑器的常见情况选择的。对于长时间保持编辑器挂载的应用程序 —— 聊天线程、长文档、用户可能产生数千个不同历史事件而不重新加载页面的任何场景 —— 两个设置值得显式调整。

maxDepth —— 设置 undo stack 上限 #

默认情况下 maxDepth 为 null，意味着 undo stack 是无限制的。每个单独的历史边界（参见上面的"什么构成连续输入？"）推送一个 HistoryStateEntry，它保留完整的 EditorState 快照。快照共享写时复制的 NodeMap，因此任何单个条目的边际成本很小，但不是零 —— 无限制的 stack 会随时间积累长尾。

设置有限的 maxDepth 以将 stack 保持为固定长度。扩展会 FIFO 淘汰超过上限的最旧条目；较旧的快照变得不可达并可以被收集。

import {configExtension, defineExtension} from 'lexical';
import {HistoryExtension} from '@lexical/history';

const editorExtension = defineExtension({
  // ...
  dependencies: [
    // 100 个事件是一个合理的起点 —— 它匹配
    // ProseMirror history plugin 的默认深度，并支持
    // 足够深的 undo stack 用于几乎任何交互式编辑会话。
    configExtension(HistoryExtension, {maxDepth: 100}),
  ],
});

上限也作为 HistoryExtension.output.maxDepth 上的可写信号暴露，因此可以在运行时重新配置（新值适用于未来的推送 —— 当上限降低时，当前 stack 不会追溯修剪）。

delay —— 更积极地合并 #

delay 是相邻编辑折叠到当前历史条目而不是推送新条目的合并窗口。默认值为 300ms。较长的延迟意味着相同输入突发产生较少的历史事件，这：

  • 降低 undoStack 增长的速率，乘以任何 maxDepth 上限的效果
  • 给用户提供匹配其写作更大语义块的撤销手势

对于重文本编辑器，500–1000ms 范围内的值是常见的 —— ProseMirror 的 history plugin 默认为 newGroupDelay: 500ms。

configExtension(HistoryExtension, {delay: 500, maxDepth: 100}),

何时不应该限制历史 #

如果您的编辑器是短期的（仅在模态、页面表单或单个消息草稿的持续时间内挂载），并且撤销期望回到文档的初始状态，默认的 maxDepth: null 就可以 —— stack 将随编辑器实例一起丢弃。上限对于编辑器是长期存在且可以在不卸载的情况下积累数千个不同历史事件时才有意义。
