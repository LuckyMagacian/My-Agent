Shadow DOM and iframes

当 Lexical 编辑器的 contentEditable 位于一个 open DOM ShadowRoot 内（例如在 web component 内）或 <iframe> 文档内时，它可以正常工作。两者都开箱即用支持 —— 您只需要将编辑器指向正确的根元素。

在 Shadow Root 中嵌入 #

附加一个 open shadow root，在其中渲染一个 contentEditable，并将该元素传递给 editor.setRootElement（或使用 @lexical/react，将 ContentEditable portal 到 shadow root 中 —— React context 跨 portal 流动，因此编辑器的构建方式与在 light DOM 中完全相同）：

const host = document.querySelector('#editor-host');
const shadow = host.attachShadow({mode: 'open'});
const contentEditable = document.createElement('div');
contentEditable.contentEditable = 'true';
shadow.appendChild(contentEditable);

editor.setRootElement(contentEditable);

Lexical 从根元素检测 enclosing shadow root 并通过它解析 selection。无需其他配置。

为什么需要平台支持 #

在 shadow tree 内，浏览器将文档的 selection 重新定位到 shadow host：Selection.anchorNode/focusNode 和 Selection.getRangeAt 报告 host 元素，而不是光标实际所在的节点，document.activeElement 报告 host 而不是聚焦的元素。Lexical 仅使用标准平台 API 解决此问题：

  • Selection 使用 Selection.getComposedRanges 和 Selection.direction 读取，它们返回真实的（未重新定位的）边界点。
  • Focus 通过 ShadowRoot.activeElement 和 Node.getRootNode 读取。
  • 光标移动和单词/行删除使用原生 Selection.modify，selection 使用 Selection.setBaseAndExtent 写入，两者都直接操作 shadow-tree 节点。
  • Drop target 和 image-drag hit-test 通过带 shadowRoots 选项的 Document.caretPositionFromPoint 解析，因此 dropped point 落在真实节点上而不是重新定位的 host。

浏览器支持 #

Shadow-aware 路径需要上面列出的平台 API。当这些 API 缺失时，Lexical 回退到 light-DOM 读取，因此不在 shadow tree 中的编辑器可以在 Lexical 支持的任何引擎上继续工作。

Platform API 用途 Chrome / Edge Firefox Safari
Selection.getComposedRanges 读取未重新定位的边界点 137+ 142+ 17.0+
Selection.direction 将 composed range 映射回 anchor/focus 137+ 126+ 17.0+
ShadowRoot.activeElement 通过 host 解析聚焦元素 All modern All modern All modern
Document.caretPositionFromPoint({shadowRoots}) Shadow-aware drop / drag hit-tests 128+ (not yet) 18.1+

Lexical 还支持 Safari 17 / 17.1 提供的 getComposedRanges 传统可变参数形式，在运行时自动选择字典或可变参数调用形式。

Closed Shadow Roots #

警告

Closed shadow root（{mode: 'closed'}）将其内容隐藏在外部代码之外：Node.getRootNode({composed: false}) 在每次外部探测时返回 host，Selection.getComposedRanges({shadowRoots}) 忽略 closed root。closed shadow root 内的编辑器无法通过 host 读取自己的 selection，因此 closed shadow roots 不支持。

如果您需要样式/标记封装而没有 selection 隔离，请使用带 delegatesFocus: true 的 open shadow root 来挂载编辑器 —— 外部代码仍然可以观察 focus 和 selection，同时 CSS 和标记保持封装。

样式 #

Shadow tree 不继承文档的样式表，因此您的编辑器/主题 CSS 必须位于 shadow root 内。附加到 root 的 <style> 元素是最简单的选项；通过 shadowRoot.adoptedStyleSheets 采用的 constructable stylesheet 在一个样式表服务于多个编辑器实例时扩展性更好。Playground 的 ShadowDomWrapper 将页面的现有 <link> / <style> 节点克隆到 shadow root 中，以便它可以重用 Vite 的 HMR-managed 样式表。这是 Shadow DOM 的属性，不是 Lexical 的。

在 iframe 中嵌入 #

根元素属于 <iframe> 文档的编辑器也受支持。Lexical 从根元素（rootElement.ownerDocument.defaultView）读取编辑器的 window/document，因此 selection 和 focus 是针对 iframe 而不是顶级文档解析的：

const iframeDoc = iframe.contentDocument;
const contentEditable = iframeDoc.querySelector('#editor');

// createEditor / setRootElement 可以在父 frame 中运行；编辑器使用
// iframe 自己的 window 和 document 进行 selection 和 focus。
editor.setRootElement(contentEditable);

iframe 内的 selection 不会被重新定位（iframe 是单独的文档，不是 shadow boundary），因此 getComposedRanges 不涉及此处 —— iframe 自己的 selection 已经报告正确的节点。

Shadow-aware 辅助函数 #

如果插件直接读取 DOM selection 或聚焦元素，请使用从 lexical 导出的 shadow/iframe-aware 辅助函数而不是 Selection.anchorNode / document.activeElement，以便在这些上下文中继续工作。在普通 light DOM 中，每个辅助函数都回退到标准读取，没有任何额外成本。

替代 使用
Selection.anchorNode / anchorOffset / focusNode / focusOffset getDOMSelectionPoints(selection, rootElement)
selection.getRangeAt(0) getDOMSelectionRange(selection, rootElement)
一次读取获取两种形式 getDOMSelectionRangeAndPoints(selection, rootElement)
selection.getComposedRanges 原始调用 getComposedStaticRange(selection, rootElement)
document.activeElement === el getActiveElement(el) === el
通过嵌套 shadow tree 获取最深聚焦元素 getActiveElementDeep(document)
在 shadow boundary 上方监听 composed: true 事件的 event.target getComposedEventTarget(event)
node.getRootNode() instanceof ShadowRoot（跨 realm 安全） isDOMShadowRoot(node)
向上遍历发现 enclosing shadow roots getDOMShadowRoots(node)

所有九个辅助函数都标记为 @experimental，因为表面正在稳定 —— 返回形式可能更改，但 light DOM 中的行为是稳定的。

常见陷阱 #

将现有编辑器移入 shadow root 会暴露一些常见的 DOM API 您可能使用的方式与它们报告的内容之间的不匹配。

Event retargeting

Shadow boundary 上方的 listener —— window、document 的 selectionchange、portal 到 document.body 的弹出窗口 —— 看到 event.target 重新定位到 shadow host，而不是实际点击的元素。rootElement.contains(event.target) 门因此总是拒绝来自编辑器的点击。通过 composed path 解析：

const target = getComposedEventTarget(event);
if (target instanceof Node && rootElement.contains(target)) {
  // 点击确实落在 shadow-hosted 编辑器内
}

Focus probes

document.activeElement 当 focus 在 open shadow tree 内时报告 host，因此 document.activeElement === rootElement 总是 false。getActiveElement(rootElement) 通过 Node.getRootNode 读取 DocumentOrShadowRoot.activeElement，而 getActiveElementDeep 在装饰器嵌入 web component 的编辑器需要最内层聚焦元素时继续下降到嵌套 shadow root。

Outside-click handlers

典型的下拉菜单注册 document.addEventListener('click', ...) 并在 button.contains(event.target) 为 false 时调用 setShowDropDown(false)。从 shadow tree 内，该检查总是失败（target 是 host），因此下拉菜单在打开它的同一点击时关闭。改为比较 getComposedEventTarget(event) —— 这是 Lexical 的 LexicalMenu 和 playground 的 DropDown 使用的相同修复。

示例 #
