Lexical 扩展

Extensions 是一种新的约定，用于以模块化和框架无关的方式向 Lexical 编辑器添加配置和行为。它比之前的 React 插件方案更易用且更强大，并且是框架无关的。

请参阅 内置扩展 查看 Lexical 及其相关包中包含的扩展列表。

使用场景 #

Lexical Extensions 允许在单一位置向编辑器添加复杂功能。如果你想要一个支持清单列表（check lists）的编辑器，只需将 CheckListExtension 添加到依赖中。所有相关的配置、注册以及对其他扩展的依赖都被封装在一起。Extensions 无论是否使用 React 都以相同方式工作，因此通常不需要单独的文档和导出来支持两者。

所有关于如何以及何时需要发生某些事情的复杂性都移到了 buildEditorFromExtensions 和扩展本身的定义中。

相比之下，在没有 Lexical Extensions 的情况下使用清单列表需要配置 ListNode 和 ListItemNode，并且需要分别注册 ListPlugin 和 CheckListPlugin 各恰好一次（如果不使用 React：则使用 registerList 和 registerCheckList）。

在没有 Lexical Extensions 的情况下自定义 Lexical 编辑器分两个阶段：

  • 构建编辑器之前的配置（注册节点、节点替换、主题等）
  • 构建编辑器之后的注册（监听器、变换、命令、React 插件等）

在许多情况下，向编辑器添加功能需要同时进行配置和注册。这通常发生在代码中非常不同的位置，甚至可能是不同的文件，并且没有传递依赖。你需要确保每个必需的配置和注册代码片段都在正确的位置恰好包含一次。当某些依赖配置或注册缺失（或运行两次！）时，最好的情况是运行时错误，但通常它会部分工作，这很难调试。

Extensions 的另一个引人注目的用例是从一个扩展向另一个扩展提供功能（例如与 yjs 协作），或者让一个扩展增强另一个扩展的能力（例如 markdown 导入/导出、向菜单或工具栏添加选项等）。这在旧版插件中非常笨拙且容易出错，因为没有既定的模式让它们相互依赖，而且用 React 提供此类功能需要严格的上下文提供者层级结构。任何扩展都可以提供输出，这相当于具有编辑器范围的扩展特定上下文。

核心 API 概览 #

Extensions 的主要用例是从扩展集合构建编辑器。任何特定于编辑器的配置或行为都应作为扩展提供，使用 defineExtension 或作为某些依赖配置的覆盖使用 configExtension。这通过以下方式完成：

  • buildEditorFromExtensions - 不使用 React 时
  • LexicalExtensionComposer - 使用 React 时

请参阅 定义扩展 获取 defineExtension 的详细指南。

以下函数包含在核心 lexical 模块中，以确保定义扩展是轻量级的，且不依赖于 @lexical/extension 的运行时功能。这些函数主要用于类型推断，实现非常简单。

  • defineExtension - 定义扩展
  • configExtension - 为扩展提供配置覆盖
  • declarePeerDependency - 通过名称声明对另一个扩展的间接依赖
  • safeCast - TypeScript 类型转换的便利工具，比 as 更安全。类似于使用带有声明类型的变量。
  • shallowMergeConfig - 默认配置合并策略

高级功能 #

  • Signals - 可用于扩展在运行时更改其配置或行为，例如动态启用或禁用扩展。这也用于优化订阅和监听器的性能。
  • Peer Dependencies - 用于声明扩展之间的间接或可选依赖，可用于仅当某个其他扩展可用时才启用某些功能或配置。例如，Emoji 扩展可能为 EmojiNode 声明特定的 Markdown 序列化，但仅在 Markdown 扩展存在时才生效。
