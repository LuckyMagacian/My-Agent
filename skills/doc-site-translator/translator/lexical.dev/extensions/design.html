指导原则​

最小化样板代码​

在可能的情况下，应提供合理的默认值，并且必须能够覆盖它们。这就是为什么 Extension 有 config 属性来指定初始配置。

完全向后兼容​

几乎所有你在编辑器或传统 React 插件中所做的事情都应该能够正常工作。升级到使用 Extension 应该是一个简单的改动。

最小化添加 Extension 所需的改动​

理想情况下，添加一个扩展应该是两三行代码：

  • 导入它
  • 将其作为依赖添加（如有必要则添加配置）
  • 添加 UI 相关代码（仅在需要时，例如必须在 DOM 的特定位置渲染）

避免无效状态​

TypeScript 在这方面有很大帮助，但它只能和 API 设计一样好。例如，将 Extension 的工作流拆分为单独的 Config、Init 和 Output 类型是随着时间推移而演进的。在早期的原型中，Config 被重载来维护所有这些状态，但这需要更多的运行时支持和类型断言来检查状态是否已在该阶段正确初始化。

尽量避免难以理解的类型错误​

从复杂的类型表达式中生成可读的错误消息能做的有限，因此 API 的设计在可能的情况下避免了这些问题。另见 microsoft/TypeScript#23689。

灵感来源​

ESLint Flat Plugins​

这些插件与本项目有许多相同的约束，当然它们用于非常不同的目的。

MDXEditor​

这个编辑器基于 Lexical，但基于第三方状态管理库提供了自己的插件机制。这些插件并没有真正公开任何类型安全的配置。

@payloadcms/richtext-lexical​

另一个基于 Lexical 的编辑器框架，用于 Payload CMS 内部。它也没有真正公开类型安全的配置，但确实似乎有很多功能，并且在延迟加载和 SSR 方面设计得很好。功能在概念上类似于 Extensions。

Effect​

这个库几乎是类型安全的最高水平，专注于组合性和可用性。

与 LexicalEditor 的更紧密集成​

这个包最初是作为完全可选的功能进行原型的，随着采用的增加，预计 Lexical 的更多部分将直接依赖它。

有意为之的权衡​

不支持编译时的依赖解析​

目前的理论是，这需要太多的 TypeScript 来携带图中存在的所有依赖项名称列表，并且可能会给 LexicalExtension 添加另一个类型参数。

这阻碍的功能包括：

  • 检测 Extension 冲突的编译时支持。检测两个以相同名称定义的扩展（但不是相同的对象引用，因为依赖项可以共享！）在 TypeScript 中也是相当大的工程。这由构建器在运行时自动检测。
  • 没有默认值的必需配置的编译时支持。扩展可以在 init 或 register 中在运行时实现此功能。
  • 必需的 peer dependencies 的编译时支持。这种情况的一个用例是要求由 LexicalExtensionComposer 或 ReactPluginHost 提供的 RectProviderExtension。扩展可以在 init 或 register 中在运行时实现此功能。

总的来说，所有这些都已经作为运行时错误出现，在构建编辑器时提供了足够的信息来快速追踪根本原因。

RSC/SSR/Headless 的文档化模式​

拥有一个用于声明 SSR 的已知 peer dependency 可能有助于指导未来的 Extension 开发。在许多情况下，存在一些具有 React 依赖的装饰器节点，你不希望（或不能）在 SSR 上下文中渲染它们。例如，RSC 无法在当前使用 React.Context 的任何地方得到支持，而这正是 Lexical 中当前使用 React 的所有地方。

另一个选择是为 SSR 使用场景构建单独的入口点，这更像是一个 RSC 特定的策略，但我们可以鼓励人们即使在原生 JS 或其他定制的 SSR 使用场景中也使用这些导入条件。这种策略可能难以在同一个模块中同时支持"headless"和"non-headless"。
