常见问题

兼容性情况如何？​

所有传统 Plugins（React 组件）都与 Lexical Extensions 兼容！

Lexical Extensions 仅与使用 Lexical Extension API（buildEditorFromExtensions，或在内部使用它的抽象如 LexicalExtensionComposer）创建的编辑器兼容。

详见 迁移指南 获取更详细的示例！

为什么叫 Extension 而不是 Plugin？​

历史原因。历史上，Lexical 使用 Plugin 这个术语来指代一个向编辑器添加行为的 React 组件。将这个词转换为另一个含义会造成困惑。

对于公共 API 来说，这也会是一个棘手的转换，因为理想的导出名称已经被占用，所以如果传统 Plugin 和新的 Extension 都叫 Plugin，它们就无法共存！

懒加载怎么办？​

懒加载不需要任何特殊支持！你用 extensions 实现的所有函数必须是同步的，但你的 register 或 afterRegistration 函数可以执行异步的 import()、网络调用等。你只需要确保你返回的 dispose 函数可以适当地管理清理工作。你还可以在 state 上使用 getSignal() 获取一个 AbortSignal，这可能比接入 dispose 函数更方便。

这类似于你如何使用 React.lazy 来延迟加载实现直到它被使用。

参见 extension-vanilla-tailwind 示例来演示如何做到这一点。

note

Extension 本身必须在创建编辑器之前同步导入。Lexical 需要预先获得所有编辑器配置（包括节点）。这与不使用 Lexical Extension 没有任何不同。Lexical 核心需要重大更改才能允许在运行时更改编辑器配置。

我们如何防止加载所有框架？​

原生 JS 和 React 在 Lexical 中有第一类支持。Lexical Builder 为这两个环境编写的 Extensions 提供了一条路径，可以加载到任何编辑器中，无论页面使用什么框架。

当你依赖一个依赖 ReactExtension 的 Extension 时，如果 React provider 不存在（LexicalExtensionComposer 或 ReactPluginHostExtension），你会得到一个运行时错误。把它想象成一个未满足但必需的 peer dependency。这样你就不会困惑，如果你添加一个需要 React 的扩展但它从未正确渲染，因为 React 没有正确设置。

其他框架可以使用 Lexical Builder 公开的功能以类似的方式提供自己的集成。目前不支持或计划支持在多个框架中使用 DecoratorNode 子类，因为我很确定你可以使用 mutation listeners 来达到同样的目的。也许 decorate 方法甚至可以在某个时候被废弃！

这将如何与 Lexical Dev Tools 交互？​

所有的 Builder 元数据都在运行时存在，并且存在于 LexicalEditor 实例上，使用一个已知符号以便开发者工具可以访问它。可以做很多事情，这里举几个例子：

  • 显示 Extension 树的图表
  • 追踪哪个配置来自哪个 Extension（例如哪个节点、哪个主题属性等）
  • 追踪哪些 commands/listeners/etc. 是由哪些 Extensions 注册的（需要编辑器插桩）
